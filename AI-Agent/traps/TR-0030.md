rule: A subagent has no final_output tool in its tool list, yet the harness's ad-hoc delegate auto-generates a recipe with a response block that forces the subagent to call final_output. This creates an infinite reminder loop that max_turns does not count. Delegate via a recipe file saved without a response block (.agents/recipes/), pass max_turns in its settings, and make the deliverable an incremental disk write to a pre-agreed path — never a final-output call.
status: active
since: 2026-10-17
related:
- '[[TR-0005]]'
created: 2026-10-17
symptoms: A subagent finishes its real work, then receives a YOU-MUST-CALL-final_output reminder every few seconds and refuses (correctly — the tool is absent). Messages multiply (111 forced calls in one session), max_turns never triggers, and the deliverable file has been complete on disk since the early minutes.
cause: the harness wraps ad-hoc delegate instructions in an auto-generated Delegated-Task recipe carrying response.json_schema (a summary string). A response block makes the harness force the final_output tool, but subagents never receive that tool (verified against the llm_request logs) — the enforced loop bypasses max_turns entirely.
workaround: Delegate through a recipe file without a response block (e.g. .agents/recipes/probe.yaml), keep max_turns in the recipe settings, require incremental writes to a disk path, and cancel the task from the parent session as soon as the forced-call pattern appears. Ad-hoc delegate stays forbidden for deliverable tasks until the harness fixes the response-block injection.
fix_status: workaround

- A delegated subagent has no `final_output` tool registered in its environment: not in the registry, not in `list_functions`, not in `get_function_details`, not by a direct call, not under alternative names, not through `invokeInternal`, and not in the `tool_graph` contract — every attempt returned a failure.
- **The consequence:** the agent runs the whole research and then gets stuck trying to hand over the result until it burns through the turn cap (`max turns reached`) and loses everything it produced except what it saved itself.
- **The root cause (a session diagnosis):** an ad-hoc delegate generates a "Delegated Task" recipe with a `response.json_schema` section, so `final_output` is forced on the subagent, while the tool is not in its tool list (verified in the `llm_request` log) — and the injection loop does not count toward the turn cap, so it continued for 18 minutes and about 2.4M tokens on work that was finished in three minutes in its file.
- **The mandatory delegation procedure:** the handover is **a write to disk** at a path agreed in advance (such as `AI-Agent/handoff/research/<task-id>.md`) with an incremental save after every step, and the delegation itself goes through a recipe file without a `response` section in `.agents/recipes/` instead of a bare ad-hoc delegate.
- **A secondary lesson:** delegation with no declared turn cap and no incremental save made the owner think the agents were stuck after an hour and cancel them by hand — the time was lost and the research was redone. For every delegation: an explicit turn cap + a written output path + no fetching of giant HTML pages.
- **An upgrade update:** the upgrade fixed two parts — the subagent really works, and `max_turns` counts the loop and stops it (23 messages/minute instead of 173 messages/18 minutes). The `final_output` injection still appears even with a recipe without a `response` section, i.e. the enforcement comes from the delegation mechanism itself, not the recipe; incremental saving and the cap are the approved line of defence.
- **A later lesson:** *"a turn budget handles the decision, and a trigger after the lock handles the decision"* — a research agent reached `max turns reached` and the "file on disk" protection worked twice, but the finished text of one agent that got stuck before its first incremental save was lost (its file stayed 51 bytes). The resulting rule: the first act of any subagent is to write the skeleton of its file (frontmatter + headings) at the agreed path **before** any research, then save incrementally after every section, and check the size before declaring success — a file under a hundred bytes = a declared failure, completed from the parent session with a documented constraint.
