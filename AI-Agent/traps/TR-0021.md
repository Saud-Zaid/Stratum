Found during a long restructuring session and confirmed twice in it.

- Instance 1: a guide H2 was renamed (a numeric prefix dropped). `linkRewriteCount: 0`. A cross-file link from a resource note created earlier was left pointing at the old heading text and broke silently — caught by `audit --check links` (R12), fixed manually.
- Instance 2 (same session, about 15 renames later): an H3 was renamed. `updatedFiles` listed only one file; the OTHER known cross-file link (from the same resource note that broke in instance 1) was again left unrewritten and broke silently — caught by `audit --check links`, fixed manually.
- In between these two instances, about 14 other renames correctly rewrote every known cross-file link (verified against a pre-built map of which headings had incoming cross-file links). So this is not "always fails" or "fails for this one file" — it is intermittent, and the same source file was correct on some renames and wrong on others in the same session.
- No configuration, mode, or pattern difference was identified between successful and failed renames. Possibly related to Obsidian's metadata cache lagging behind rapid successive edits, but unconfirmed — do not assume a specific trigger.
- `find_broken_links` gives no signal either way for heading links (it flags every heading link as broken, correct and incorrect alike).
- Rule: `linkRewriteCount` and the absence of a tool error are not proof of a clean rename. Run `audit --check links` (R12) after every single `rename_heading` call — not batched at the end — so a silent failure is caught and fixed before compounding with the next rename. Do not skip verification for a file that succeeded on a previous rename in the same session; it can fail on the next one.
