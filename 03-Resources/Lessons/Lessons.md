# Lessons

One line per lesson. A lesson is general when it rests on a principle independent of one Area's specifics, or recurred in two Areas; lessons from one Area wait in its own changelog until the monthly review promotes them ([[Second-Brain-User-Guide]]).

## Structure and classification

1. **Never record the same fact in two places** — the PARA folder is not a `type` field.
2. **Do not skip the Zettelkasten stages** — raw capture, then a source note, then a permanent idea.
3. **PARA and Zettelkasten need an explicit intersection** — a MOC plus the monthly review.
4. **Naming rules are written on day one.**
5. **Do not impose Folgezettel unless your way of thinking needs it.**
6. **A PARA folder without an official template yields inconsistent notes.**
7. **A field that shows up in practice although the design lacks it means an incomplete design, not wrong use.**
8. **MCP tools have real limits that need documenting — but the limits themselves change, so periodic verification is necessary.**

## What counts as an Area, a Project, a Resource

9. **Personal or reflective content with no actionability does not enter PARA as an Area.**
10. **A Resource can be a tool you run, not only a reference you read.**
11. **A Project has a natural end even inside a larger ongoing commitment.**
12. **A "campaign" with an undated final goal is a Project, not an Area.**
13. **Several initiatives under one party are one unified Area, not an Area per initiative.**

## Sources and notes

14. **A source you run (code/a tool) deserves a parallel note type, not a squeeze into a read-source template.**
15. **Several sources on the same topic are not squeezed into one note.**
16. **An existing mechanism (derived-from, multi-link) covers a new need (synthesis) without a new type.**
17. **Separating the goal from its side effect protects the goal from drifting.**
18. **A queryable field (frontmatter) beats a checkbox when it feeds a real dashboard.**
19. **A deliberate, agreed structural excess differs from an unjustified one.**
20. **Immediate classification at the moment of capture contradicts standard practice — the decision is deferred to a later review.**
21. **Avoid scattering the same story across several files: use progressive summarization.**
22. **An invented tag (`#candidate-for-permanent`) was dropped in favour of the field that already exists, `content_candidate`.**

## Review and maintenance

23. **Reviewing templates periodically reveals silent gaps — and guidance moves from YAML into the note body.**
24. **A lesson from one Area may be a general principle, not a local quirk — the decision is deferred to a retroactive review.**
25. **A periodic review of an AI agent is a set of discovery tasks with real tools, not a copied human checklist.**
26. **A rarely recurring finding is neither deleted nor left in a confusing temporary stop — it gets a permanent home with no deletion.**
27. **A tag is a temporary search tool that turns into a permanent link on accumulation, not a permanent analytic classification by itself.**
28. **An activity state (`review_tier: active/dormant`) stops the periodic review from bloating as the number of Areas grows.**
29. **An architectural review uses the "the heading is a promise" criterion, not a manual counter or an arbitrary number.**
30. **A read-back after every write is mandatory, not optional — a tool's success confirmation alone is not enough.**
